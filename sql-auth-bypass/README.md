# SQL injection: authentication bypass

**Assigned owner:** Rushal Verma, IIT2024045.

This module compares a vulnerable login against a login using parameterized queries. Both use the same database, accounts, and query conditions; the SQL construction is the important difference.

## Start the application

From this directory, with Python 3.10+ installed:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

Open http://127.0.0.1:5000. Stop with Ctrl+C. If port 5000 is occupied, set `$env:SQLI_LAB_PORT = '5050'` before starting and use http://127.0.0.1:5050. The app binds only to `127.0.0.1` and disables the debugger. On macOS/Linux use `.venv/bin/python` for the virtual environment executable and `SQLI_LAB_PORT=5050 .venv/bin/python app.py` to select another port.

SQLite creates `instance/lab.sqlite3` automatically. No external database, credentials, or account setup is required. Sessions are cleared by a server restart because a new random signing key is generated at startup.

## Exact demonstration

| Step | Page | Username | Password | Expected result |
| --- | --- | --- | --- | --- |
| 1. Normal rejection | `/login/vulnerable` | `admin` | `wrong-password` | Login rejected |
| 2. Bypass | `/login/vulnerable` | `admin' -- ` | `wrong-password` | Login successful as admin |
| 3. Protected content | Click Open account dashboard | - | - | Dashboard identifies admin |
| 4. Same attack after fix | `/login/parameterized` | `admin' -- ` | `wrong-password` | Login rejected |
| 5. Normal login after fix | `/login/parameterized` | `admin` | `AdminDemo42!` | Login successful |

The attack username ends with one space after `--`. Copy it exactly from this code block:

```text
admin' -- 
```

The same value is available under **Show the assignment test input** in the app. The vulnerable query generated by that input is:

```sql
SELECT id, username, role FROM users WHERE username = 'admin' -- ' AND password = 'wrong-password'
```

The quote closes the username string. SQLite treats the rest of the line after `--` as a comment. The database therefore evaluates the username condition without the password condition and returns the admin row. The application incorrectly treats that row as sufficient proof of authentication and creates an authenticated session.

**Root cause:** The application concatenates untrusted input into SQL syntax. A crafted username changes the structure of the login query and comments out its password check.

## Vulnerable code and implemented mitigation

In `app.py`, read `authenticate_vulnerable` and `authenticate_parameterized`.

Vulnerable code:

```python
query = (
    "SELECT id, username, role FROM users "
    f"WHERE username = '{username}' AND password = '{password}'"
)
user = connection.execute(query).fetchone()
```

Fixed code:

```python
query = "SELECT id, username, role FROM users WHERE username = ? AND password = ?"
user = connection.execute(query, (username, password)).fetchone()
```

The `?` placeholders bind data values. The driver does not splice the username into the statement as SQL source. The database looks for a literal username containing `admin' -- `; there is no such dummy account, so no row is returned. Correct credentials still work. The interface shows the fixed template and its bound values separately; it does not claim that a manually interpolated query was executed.

The vulnerable and fixed versions keep separate login sessions. A failed retry clears that version's earlier login, so stale authentication cannot make a failed exploit look successful. `/dashboard/<mode>` really checks the session; it is not just a success message on an unprotected page.

## Other mitigation options (theory)

Allow-list validation enforces expected input formats, and is especially useful for SQL identifiers such as column names that cannot be supplied as ordinary value parameters. It supplements parameter binding; rejecting a few punctuation characters is not a general SQL injection defense. Least-privilege database access reduces what an exploited application can read or modify, but does not fix a vulnerable query. SQLite is embedded and has no database-user roles like a client/server database; discuss restricted OS file permissions here and limited database accounts for PostgreSQL/MySQL. Safe error handling returns generic failures rather than exposing schema details or SQL exceptions, reducing information leakage without preventing injection itself. In this implementation parameter binding is the primary injection fix; generic errors are also returned.

## Deliberate simplifications

This is a SQL injection lesson, not a production login system. Dummy passwords are stored as plaintext so the two query paths differ only in query construction. Production applications should store slow, salted password hashes, look up the user with a parameterized query, and verify the hash in application code. Password hashing alone does not fix SQL injection. The lab also omits production requirements such as HTTPS, rate limiting, full CSRF protection, and account recovery. A successful mitigation demonstration means the demonstrated injection is fixed, not that every possible security issue is resolved.
